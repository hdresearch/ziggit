# Ziggit Feature Completion Plan

This plan covers implementing the missing features to make ziggit a complete git implementation — including a fully functional git server, delta encoding, full shallow clone support, libgit2 verification testing, and comprehensive test coverage.

**Do NOT cut any releases during this work. Releases will be done manually.**

---

## Phase 1: Delta Encoding (Create)

**Goal:** `pack-objects` produces real deltas instead of `"Total N (delta 0)"`.

**Why:** Every other git implementation (C git, libgit2, go-git, gitoxide, JGit) computes deltas. Without this, packs generated by ziggit are 2-10x larger than necessary. This is also a prerequisite for the git server (Phase 3) to serve efficient fetches.

### 1.1 Implement delta creation algorithm

**File:** `src/git/delta_encode.zig` (new)

- Implement the git delta format encoder. The format is documented in `git/Documentation/technical/pack-format.txt` and consists of:
  - A source-size varint
  - A target-size varint
  - A series of instructions: either COPY (copy N bytes from offset O in source) or INSERT (insert N literal bytes)
- The core algorithm:
  1. Build a hash index of 16-byte windows over the source (base) object
  2. Slide over the target object, looking up each 16-byte window in the index
  3. On match: emit a COPY instruction spanning the longest matching run
  4. On no match: accumulate bytes into an INSERT instruction (max 127 bytes per INSERT)
- Function signatures:
  ```zig
  pub fn createDelta(allocator: Allocator, base: []const u8, target: []const u8) ![]u8
  pub fn deltaSize(base: []const u8, target: []const u8) usize  // estimate without allocating
  ```
- Reference implementation: `git/diff-delta.c` (440 lines of C)

### 1.2 Integrate into pack-objects

**File:** `src/cmd_pack.zig`

- After collecting all objects, sort by type then size (git's heuristic for finding good delta bases)
- For each object, try delta against the N most recent objects of the same type (window size, default 10)
- If delta is smaller than the full object, store as OFS_DELTA or REF_DELTA in the pack
- Update the pack header object count and checksum
- Change the progress output from `"delta 0"` to the actual delta count

### 1.3 Integrate into push pack generation

**File:** `src/git/smart_http.zig` → `generatePackForPush()`

- When building a pack for push, use delta encoding for objects that share type/similarity
- This reduces push payload size significantly

### 1.4 Tests

**File:** `test/delta_encode_test.zig` (new)

- **Roundtrip test:** `createDelta(base, target)` → `applyDelta(base, delta)` → verify equals target
- **Known-value test:** Create delta for a known base/target pair, verify output matches expected bytes
- **Empty/identical test:** Delta of identical objects should be tiny; delta of empty base should be full INSERT
- **Large object test:** 1MB+ objects with small differences → delta should be << full size
- **Cross-validation:** Generate a pack with ziggit's deltas, verify with `git verify-pack -v` and `git index-pack`
- **git CLI parity:** Clone a repo with `git`, repack with ziggit's `pack-objects`, verify `git fsck` passes

## Phase 2: Shallow Clone Completion (deepen-since, deepen-relative)

**Goal:** Full shallow clone support matching git's capabilities.

### 2.1 deepen-since (client side)

**File:** `src/git/smart_http.zig`

- Currently advertised in capabilities but never sent
- Add `buildUploadPackRequestWithDeepenSince(allocator, wants, haves, timestamp)` that emits `deepen-since <unix-timestamp>\n` instead of `deepen N`
- Wire into `ziggit fetch --shallow-since=<date>` and `ziggit clone --shallow-since=<date>`
- Parse the server's `shallow <hash>` / `unshallow <hash>` response lines to update `.git/shallow`

### 2.2 deepen-relative (client side)

**File:** `src/git/smart_http.zig`

- Add `deepen-relative` capability advertisement
- When doing `ziggit fetch --deepen=N` on an already-shallow repo, send `deepen-relative` + `deepen N` to extend the shallow boundary by N commits rather than setting absolute depth
- Update `.git/shallow` file with new boundary commits

### 2.3 deepen-since / deepen-relative (server side — needed for Phase 3)

**File:** `src/git/git_serve.zig` (new, see Phase 3)

- Server must parse `deepen-since <timestamp>` from client request
- Walk commit history, stop at commits older than timestamp
- Emit `shallow <hash>` lines for the boundary commits
- For `deepen-relative`: read client's existing shallow boundary, extend by N

## Phase 3: Git Server

**Goal:** A pure-Zig git server that can serve `git clone`, `git fetch`, `git pull`, and `git push` from any standard git client. Both as a native binary (`ziggit serve`) and as a WASM module with host-callback storage.

### 3.1 Server protocol handler — git-upload-pack (serve fetch/clone)

**File:** `src/git/git_serve.zig` (new, ~800-1200 lines estimated)

**Functions:**

```zig
/// Handle a complete git-upload-pack session (v1).
/// Reads the client's want/have lines, computes which objects to send,
/// generates a pack, and writes it to the output writer.
pub fn serveUploadPackV1(
    allocator: Allocator,
    storage: *GitStorage,       // abstraction over filesystem or KV store
    reader: anytype,            // client request bytes
    writer: anytype,            // response output (streaming)
) !void

/// Handle git-upload-pack protocol v2 (ls-refs + fetch commands).
pub fn serveUploadPackV2(
    allocator: Allocator,
    storage: *GitStorage,
    reader: anytype,
    writer: anytype,
) !void
```

**Protocol v1 flow:**
1. Advertise refs: read all refs from storage, format as pkt-lines with capabilities (`side-band-64k ofs-delta shallow deepen-since deepen-relative deepen-not no-progress`)
2. Parse client's `want` lines (what they need) and `have` lines (what they already have)
3. Negotiate: for each `have`, check if object exists in storage. Send `ACK` for known objects.
4. After `done` from client: compute the set of objects to send (wants minus haves, walking the commit graph)
5. Generate pack using delta encoding (Phase 1) — prefer stored deltas from previous pushes when base objects match client's haves
6. Stream pack data through sideband channel 1, progress on channel 2

**Protocol v2 flow:**
1. Advertise capabilities: `version 2\n` + `ls-refs\n` + `fetch=shallow\n`
2. Handle `command=ls-refs`: return filtered ref list based on `ref-prefix` arguments
3. Handle `command=fetch`: parse `want`/`have`/`done`/`deepen`/`deepen-since`/`deepen-relative` arguments, compute and stream pack

### 3.2 Server protocol handler — git-receive-pack (serve push)

**File:** `src/git/git_serve.zig` (continued)

```zig
/// Handle a complete git-receive-pack session.
pub fn serveReceivePack(
    allocator: Allocator,
    storage: *GitStorage,
    reader: anytype,
    writer: anytype,
) !void
```

**Flow:**
1. Advertise refs with `report-status` capability
2. Parse ref update lines: `<old-hash> <new-hash> <refname>`
3. Receive pack data from client
4. Index the pack: resolve all objects, verify checksums
5. **Store raw deltas alongside resolved objects** (for efficient future fetches — see 3.4)
6. Update refs atomically
7. Send status report: `unpack ok\n` + per-ref `ok <refname>\n` or `ng <refname> <reason>\n`

### 3.3 Storage abstraction

**File:** `src/git/git_storage.zig` (new)

```zig
pub const GitStorage = struct {
    // Virtual dispatch table for different storage backends
    getObjectFn: *const fn (self: *GitStorage, hash: [20]u8) ?StoredObject,
    putObjectFn: *const fn (self: *GitStorage, hash: [20]u8, obj: StoredObject) !void,
    getRefFn: *const fn (self: *GitStorage, name: []const u8) ?[20]u8,
    putRefFn: *const fn (self: *GitStorage, name: []const u8, hash: [20]u8) !void,
    deleteRefFn: *const fn (self: *GitStorage, name: []const u8) !void,
    listRefsFn: *const fn (self: *GitStorage, allocator: Allocator) ![]RefEntry,
    // ... additional methods for notes, listing objects, etc.
};

pub const StoredObject = struct {
    obj_type: ObjectType,  // commit, tree, blob, tag
    data: []const u8,      // full resolved object content
    // Optional: stored delta from the original push
    delta_base: ?[20]u8,
    delta_data: ?[]const u8,
};
```

**Two backends:**
1. **FilesystemStorage** — stores objects in `.git/objects/` (loose) and `.git/objects/pack/` (packed), exactly like normal git. For the `ziggit serve` command.
2. **HostCallbackStorage** — for WASM builds. Delegates to `host_get_object`, `host_put_object`, etc. extern functions. The JS host implements these against whatever backing store it wants (SQLite, KV, memory, etc.).

### 3.4 Delta persistence (store-and-replay optimization)

When receiving a push, in addition to resolving deltas to full objects, **persist the raw delta bytes and base hash** alongside each object in storage. On fetch, if the requesting client already has the base object (it's in their `have` list), emit the stored delta instead of the full object. This avoids the expensive delta computation on serve and reduces memory usage.

**Implementation:** Add `delta_base` and `delta_data` fields to `StoredObject`. In `serveUploadPackV1/V2`, when building the pack, check each object: if it has a stored delta and the base is in the client's `have` set, emit as OFS_DELTA/REF_DELTA using the stored bytes.

### 3.5 Native server command: `ziggit serve`

**File:** `src/cmd_serve.zig` (new)

```
ziggit serve [--port=9418] [--http-port=8080] [--base-path=/path/to/repos]
```

- Listen on HTTP, serve smart HTTP git protocol
- Route `GET /repo.git/info/refs?service=git-upload-pack` → ref advertisement
- Route `POST /repo.git/git-upload-pack` → serve fetch/clone
- Route `POST /repo.git/git-receive-pack` → serve push
- Uses `FilesystemStorage` backend
- Single-threaded event loop (Zig's `std.net.Server` or `std.http.Server`)

### 3.7 Streaming output

All server response generation should call `host_emit_bytes` (WASM) or write to the response writer (native) incrementally as pack data is generated. This means:

- Pack header is emitted first
- Each object/delta is compressed and emitted as it's generated (not buffered in full)
- Sideband framing wraps each chunk
- Pack checksum is emitted last

This requires modifying the pack generation code to write to a `Writer` interface rather than an `ArrayList`.
